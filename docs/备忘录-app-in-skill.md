# 备忘录：App-in-Skill 和 Claude Mobile 是同一个问题的两半

给 Claude Mobile 作者。读完一篇叫 App-in-Skill 的 paper（Kelly Peilin Chan, 2026.06），我觉得它和你这个项目咬得很紧，值得你花二十分钟看一眼原文。下面先说为什么相关，再说它能直接帮到你哪里，最后说一处你们设计上的真实分歧——那处分歧反而是机会。

## 你们在解同一个问题，只是从两头进

你的 README 第一句就点破了：官方 Claude 手机端只能聊天，碰不到电脑上的东西，而你真正想做的活——改文档、翻客户资料、跑脚本、导 PDF——都要真实的文件读写和命令执行。你的答案是把全能力的 claude-code 搬到手机网页上。

这篇 paper 从另一头进。它的观察是：agent 已经接近全能，瓶颈是人——而瓶颈不是人的判断力，是缺一个能高效施加判断、并和别人共享的界面。聊天是个糟糕的操作面：一旦工作流涉及很多条目、持久状态、人工审批，或者要交给第二个人，往上滚的聊天记录就撑不住了。它的答案是让 skill 除了回文字，还能临时开一个本地网页当"白板"。

一句话对比：**你把聊天搬上了手机；这篇 paper 说光有聊天不够，得在聊天旁边给它一块白板。** 你已经把最难的那部分搭好了——一个常驻后端、按角色隔离的 cwd、真实权限、产物渲染、私有网络当门禁。paper 描述的那块白板，几乎就是缺在你 `Chat.tsx` 旁边的一个面板。

## 它能直接帮你的地方

### 1. 你的 `ArtifactView` 已经是半个 App-in-Skill，差一个回写通道

你现在的产物渲染是单向的：claude-code 产出 PDF / HTML / 图片，你在 `/files/:id/*` 把它流回手机，在 sandbox iframe 里渲染。人只能看，不能在上面做结构化决策再喂回去。

paper 的核心机制正是补上这条回路。它叫"文件交接"（file handoff）：skill 写一批待办到 `current_batch.json`（agent 准备好的草稿、动作、风险标签），网页渲染成可筛选的队列，人在上面批准 / 改写 / 打回 / 拦截，决策落到 `decisions.json`，skill 再读回来执行。你已经有了 `skill → 手机` 这半条（产物文件服务），缺的是 `手机 → skill` 这半条（结构化决策回写）。补上它，你的手机端就从"看产出"升级成"审一批、批一批"。

最省事的落点：在 `web/src/components/` 加一个 `ReviewQueue.tsx`，和 `Chat.tsx` 并排，数据来源是角色 cwd 下的 `.data/current_batch.json`，决策 POST 回一个新端点写 `.data/decisions.json`。你的 `FileBrowser` 已经能安全读 cwd 下的文件，这层基本是现成的。

### 2. 那条"边界"正好补上你 `bypassPermissions` 的窟窿

你在安全须知里诚实地写了：`permissionMode: "bypassPermissions"` 会让模型在该目录无确认执行任何命令，强但危险。这是手机场景的真痛点——手机上挨个点权限确认很烦，但全放开又不敢。

paper 给了一个结构性的解法，叫边界不变量（the Boundary）：**所有对外副作用（发邮件、调 API、改库、删文件）只能由 skill 发起；网页只读写本地交接文件，永不碰外部世界。** 授权检查因此永远只发生在一个地方。

把它套到你的架构上：手机网页负责"看见 + 决策"，但真正动外部世界的事，全部经过 skill 那一道、并且要求 `decisions.json` 里有一条对应的批准记录才执行。这样你不必在 `acceptEdits`（每次烦）和 `bypassPermissions`（全裸奔）之间二选一——危险动作（发出去、扣款、删除）默认需要队列里一条人工批准，普通文件编辑照旧自动过。手机上点一下"批准"，比逐条确认权限自然得多。

### 3. 一个可恢复、可交接的会话模型

你的会话设计很讲究：WebSocket 断了会话不销毁，重连回原地。但它活在内存里——后端进程一重启，正在进行的那批工作的"人做到哪了"就没了。

paper 有一条硬要求：所有工作流状态落盘，绝不只存在进程内存里，所以 agent 暂停、浏览器关掉、明天再来，决策都还在。对手机场景这条特别值钱——手机网络飘忽、随时切后台。如果"待审的一批 + 已做的决策"是 cwd 下的 `.data/` 文件而不是内存，你的 Mac mini 重启、手机断线半小时回来，那批审阅原样还在。这和你"切角色不打断对话"的诉求是同一个方向，只是把它从内存延伸到了磁盘。

### 4. 它顺手给了你一条"日抛软件"的产品故事

paper 后半段有个更大的判断：当 agent 花一段对话的成本就能生成一个贴合某工作流的小工具，软件就不必做大做全才值得做，会碎成无数小而专、用完即弃的工具。

这话对你有用，是因为你的"角色"机制已经在这条路上了。你现在一个角色绑一个 cwd + 它自己 `.claude/` 里的 skills。再往前一步，让每个角色除了带 skills，还带一个为它定制的审阅界面——销售角色一个客户跟进队列，写作角色一个改稿队列——你的 Claude Mobile 就从"手机上的 claude-code"变成"手机上一组各自带界面的工作流工具"。这个定位比"远程聊天"硬得多。

## 一处真实分歧，也是机会

得说清楚，你们有一处设计哲学不一样，别假装没有。

**Claude Mobile 是一个通用聊天外壳**——一个 React 前端，对任何角色、任何 cwd 都长一个样。**App-in-Skill 主张界面应该是按工作流定制的、由 skill 临时拉起的**——审稿队列长一个样，邮件 triage 长另一个样，是 skill 自己带的，不是一个万能前端。

这不矛盾，是分层。你的通用外壳负责那些 paper 没碰的硬骨头：跨网络的传输、私有隧道、订阅认证、多角色常驻会话、产物渲染。这些是任何 App-in-Skill 想上手机都得有、但 paper 默认在桌面本地、没解决的：

> **paper 假设 skill 能在本机 `127.0.0.1` 开个窗口给同机的浏览器看。你的项目恰好能把那个窗口送到一台远在国外、隔着防火墙的手机上。**

所以最自然的合流不是二选一，是：让你的后端能托管 skill 拉起的那个 per-workflow 界面，而不只是托管你自己写的那个通用 Chat。具体说，skill 在角色 cwd 下写出它的界面文件（paper 里那套 `app/index.html` + `.data/` 交接），你的 Fastify 把它当作该角色的一个"白板面板"服务出去——和你现在服务产物文件是同一个安全模型（`realpath` 越界校验那套直接复用）。你提供"管道 + 多角色 + 远程 + 认证"，skill 提供"这个工作流长什么样"。

## 建议的最小一步

别动你现在的架构，先验证回路：

1. 挑一个你自己高频的工作流（看你 README，"写作"角色的改稿、或客户资料的整理都行）。
2. 让那个角色的 skill 在它 cwd 下写一个 `.data/current_batch.json`（一批待审条目，每条带 before / after / 风险标签）。
3. 加一个 `ReviewQueue.tsx`，和 Chat 并排，渲染这批条目，决策 POST 到新端点写 `.data/decisions.json`。
4. 加一条规则：危险动作（发邮件 / 删除 / 对外调用）必须 `decisions.json` 里有对应批准记录，skill 才执行——这就是把那条边界落地。

跑通这一个，你就同时拿到了：手机上的批量审阅、一个比 `bypassPermissions` 安全得多的授权模型、以及一个可恢复的工作流状态。

## 一个现成的参考实现

我按这套规范给本地的 `review-writing` skill 搭了一个最小 App-in-Skill 跑通了：Node 内置 server 起在 `127.0.0.1`，findings 排成审阅队列，人点批准 / 改写 / 保留，再由一个持锁脚本按 before 文本匹配写回草稿——网页全程只碰 `.data/`，唯一改原文的是那个 skill 脚本。代码在 `~/.claude/skills/review-writing/`（`app/` + `lib/data-provider/` + `scripts/apply_decisions.mjs`），设计文档在同目录 `APP-IN-SKILL-DESIGN.md`。它是桌面本地版；你的项目要做的，是把这种东西送上手机。需要的话我可以把那套交接 schema 整理成能直接接进你 Fastify 的样子。
